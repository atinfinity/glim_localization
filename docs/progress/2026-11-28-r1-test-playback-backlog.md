# Flaky R1 launch test: glim_rosbag read-ahead, not ROS cross-talk

- **Symptom**: CI run [46022296142](https://github.com/atinfinity/glim_localization/actions/runs/46022296142) (attempt 2, `checks (rest)`, amd64): `test_launch_r1.py` failed with "90 poses for 121 frames". In the interleaved ctest output its `/initialpose received (min_stamp=4.999)` came right after `test_r2_node`'s `/initialpose: reset requested (stamp=4.999)`, which looked like an `/initialpose` crossing between parallel tests.
- **Not cross-talk**:
  - Every test of `glim_localization_ros2` that uses ROS runs through `run_test_isolated.py`: the three ROS gtests (`ament_add_ros_isolated_gtest`) and all nine launch tests (`add_launch_test ... RUNNER`, which `add_launch_test` passes on to `ament_add_test`). `ctest --show-only=json-v1` confirms it. Only the linters and the three gtests without a ROS graph run without it.
  - The runner (`domain_coordinator`, Jazzy) holds a TCP port `32768 + id` for the life of the test, so two running tests never share an id. In the failed run `test_launch_r1` had `ROS_DOMAIN_ID 3` and `test_r2_node` had 4. `scripts/test_colcon.sh` unsets `ROS_DOMAIN_ID`, and nothing sets a fixed one.
  - In R1 the `/initialpose` does not go through DDS at all: `glim_rosbag` hands bag messages of extension topics to the extension in process (`insert_message_instance`). Both tests play the same fixture bag, whose second `/initialpose` is exact ground truth at 5 s, so they log the same stamp and the same pose.
- **Root cause**: `test_launch_r1` ran `glim_rosbag` at its default `playback_speed` of 100. `glim_rosbag` reads the bag as fast as that allows and throttles only loosely on the odometry queue (`(workload - 4) * 5` ms per frame above 5 queued), so on a loaded runner it reads seconds ahead of the odometry. The extension then gets the 5 s `/initialpose` while frames before 5 s are still queued, and the reset (`min_stamp` 4.999) drops them. A frame handled more than 1 s (`GyroBuffer::WINDOW`) after the newest IMU sample is also not published (the "no IMU sample within 0.02 s" warning in the CI log). 121 - 90 = 31 frames, about 3 s of backlog. `test_r1_extension` had the same issue at its 2x.
- **Pre-existing**: yes. `test_launch_r1` has used the default playback speed since it was added (aca6bbd); the failure depends only on CPU load. It is independent of the CI parts change ([#75](https://github.com/atinfinity/glim_localization/pull/75)), which runs the same `scripts/test_colcon.sh`.
- **Change**:
  - `test_launch_r1.py` passes `config_path`: a copy of the installed `config/r1` with `glim_ros.playback_speed` 1 (the launch file still fills in the map path).
  - `test_r1_extension.py` goes from 2x to 1x.
  - `scripts/test_colcon.sh` fails when a test of `glim_localization_ros2`, other than a linter or a listed gtest without ROS, does not run through `run_test_isolated.py`.
- **Decisions**: real time, not a lower ratio or a bag without the 5 s pose. The test checks the launch plumbing, and the odometry has to keep up with real time anyway. Its own lag then stays below a frame or two even under load. It costs about 6 s per test.
- **Verification** (Docker, amd64, 16 cores, `glim_localization:dev`):
  - Each test alone with 32 busy-loop processes running beside it: the old `test_launch_r1` failed 3 of 3 (86, 93, 72 poses) and again 3 of 3 in a second set (74, 77, 95). At 2x it failed 3 of 3 (76, 88, 85), and the new one at 1x passed 9 of 9 (114 to 121 poses). `test_r1_extension` at 2x failed 3 of 3 (79 poses); at 1x it passed 10 of 11.
  - `scripts/test_colcon.sh` with `CTEST_JOBS=8`: passed 3 of 3 runs. The new check printed `ok: every ROS test of glim_localization_ros2 runs through run_test_isolated.py`. With the allowlist cut to one gtest, it failed and named the other two.
- **Open**: the one failure in 11 runs of `test_r1_extension` at 1x under 2x CPU oversubscription was not kept, so its reason is unknown; CI load is lower than that.
