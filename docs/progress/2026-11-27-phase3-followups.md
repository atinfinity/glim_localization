# Phase 3 follow-ups: test coverage ([#6](https://github.com/atinfinity/glim_localization/issues/6))

- **Change**: the test items of [#6](https://github.com/atinfinity/glim_localization/issues/6), and a check of the robustness items.
  - **The robustness items were already done.** The `v_world_imu` speed limit in `reset()` (`kMaxResetSpeed`, 100 m/s), the bias kept in `start_imu_bias_`, and rejecting `init_v_world_imu` without `init_T_world_imu` came with `bad6ddb` and `2c788e7` ([entry](2026-11-26-reset-robustness.md), with the reason for the bound). Their tests are in `test_localization_odometry.cpp` and `test_replay_tool.cpp`, and DESIGN §5.3 documents them. Only the checkboxes of the issue were not ticked. Nothing was changed for them here.
  - **`map_voxel_resolutions` order** (`test_map_manager.cpp`). `MapManager::load` accepts only a non-empty list of positive, finite, strictly ascending values; it fails on a descending list, a duplicate or an unsorted list, and does not sort. New tests, on a loadable map so that the list is the only reason for a failure (the old `RejectsInvalidResolution` used a missing path, so it passed without the check):
    - `RejectsResolutionsThatAreNotPositiveOrNotStrictlyAscending`: empty, zero, negative, NaN, infinite, descending, a duplicate (`{0.5, 0.5, 1.0}` and `{1.0, 1.0}`) and two unsorted lists; each fails and leaves the map empty.
    - `AcceptsStrictlyAscendingResolutionsInTheGivenOrder`: one, two and four levels; every tile has the levels in the given order, level 0 the finest.
  - **DEGRADED and back** (`test_localization_odometry.cpp`, `EntersAndRecoversFromDegraded`). Frames 40 to 54 get four copies of their points raised 10 to 40 m in the world, a static structure that is not in the map, so the inlier ratio falls to about 0.2 while the original points keep the map factors. The test asserts the exact state of every frame: TRACKING, DEGRADED from the 5th bad frame (`degraded_frames`), TRACKING again from the 5th good frame (`tracking_frames`), never LOST, no reset. It also checks the map factors built for every frame: wrapped in `WeightedFactor` at `degraded_weight_scale` (0.1) when the previous frame was DEGRADED, bare (weight 1) otherwise. And the pose stays within 0.1 m and 1 deg of the truth from `kSettleTime` (3 s) on. A subclass exposes the protected `current_map_factors_`.
  - **The wall-clock assertion.** The one meant is `EXPECT_LT(elapsed, 60.0)` at the end of `ConvergesFromPerturbedInitialPose`; the issue says 20 s, but the code has had 60 s since the first public commit. It is the only wall-clock bound on a whole odometry run. It is removed. In its place the test bounds the work per frame: with `max_submaps` set to 3, below the 5 tiles of the map, the largest `num_map_factors` over the run is exactly `max_submaps` times the number of levels. The elapsed time and the latencies are still printed, and ctest's `TIMEOUT 120` catches a hang.
  - **Plugin `EXPECT_DEATH`** (`test_plugin.cpp`). It now matches `failed to create odometry_localization_cpu: failed to load the localization map` instead of `""`. The module logs that line through spdlog before `std::abort()`. The default logger writes to stdout, and a death test matches stderr only, so the child sets a stderr logger first.
  - DESIGN §5.1 now states the order rule for `map_voxel_resolutions`, and §5.4 how DEGRADED returns to TRACKING.
- **Decisions**:
  - **Reject, not sort, an unordered list.** The order is what the user wrote in the config, and level 0 is used as the finest. Sorting would hide a mistake (for example a list meant for another tool). The tests pin the current behaviour; the code is not changed.
  - **Bad frames from extra structure, not from moving off the map.** Points that move with the sensor, or frames that miss the map, would also change the odometry or remove the map factors, so the test could not tell a DEGRADED that holds the pose from one that drifts. Static extra structure is the case DEGRADED is for (the scene changed since the map was made): the inlier ratio falls, and the remaining map factors and the odometry keep the pose.
  - **No wall-clock bound at all.** Any bound either flakes on a busy machine (parallel ctest, another container) or is so loose that it checks nothing; 60 s was already the second. The per-frame factor bound is deterministic and catches the main way the work per frame could grow (tiles or levels not limited). The latency is still printed, for comparison with the GPU module, but not asserted. The 2 s bound on one search iteration in `test_relocalization.cpp` (`TruncatedSearchIsRejected`) is a different check, on a deadline, and stays.
  - **Test-only logger change for the death test.** Writing the abort reason to stderr in the module itself would also work, but it would print it twice wherever the default logger already goes to the console. The module already logs and flushes the reason; only the test needs it on stderr.
- **Verification** (Docker, amd64):
  - Each new test was checked against the code without its fix: with the ascending check removed, the five order cases of `RejectsResolutionsThatAreNotPositiveOrNotStrictlyAscending` fail; with the DEGRADED weight cut removed, `EntersAndRecoversFromDegraded` fails at every DEGRADED frame (weight 1 instead of 0.1); without the stderr logger, the death test fails with "died but not with expected error". `AcceptsStrictlyAscendingResolutionsInTheGivenOrder` guards against rejecting too much, so it passes either way.
  - `scripts/ci.sh` passes: core ctest 373 of 373 (370 before, plus the three new tests), colcon test 208 results with no failures (`glim_localization_ros2` 23 of 23), Python tests 306 passed, replay e2e and the quick robustness suite pass. `glim_localization_ros2` is not changed, so it was not linted again.
- **Review** (before the pull request), fixed:
  - The factor bound could not fail: the 5 tiles are all within the 60 m search radius and the default `max_submaps` is 5, so the bound was the whole map. The test now sets `max_submaps` to 3 and requires the cap to be reached (9 factors, 3 tiles of 3 levels), which also drops the redundant "positive" check.
  - The DEGRADED weight check re-derived `map_factor_weight()`, so it did not see whether `create_map_factors` applies it. It now reads the factors built for each frame.
  - The bad window started at frame 30 (t = 3 s), exactly `kSettleTime`, so the error bound covered the tail of the convergence under the reduced weight. It now starts at frame 40, 1 s later.
  - `test_plugin.cpp` now says why the stderr logger set in the test reaches the `dlopen()`ed module: spdlog is the shared `libspdlog.so` (checked with `ldd` on the test and the module), so both share one registry.
  - Checked against sabotaged code: `MapManager::query` ignoring `k`, and `select_map_tiles` passing 1000 instead of `max_submaps`, each make `ConvergesFromPerturbedInitialPose` fail (15 factors instead of 9). `create_map_factors` ignoring its weight makes `EntersAndRecoversFromDegraded` fail at every frame after a DEGRADED one (1 instead of 0.1). With 3 tiles, the accuracy is unchanged (max 0.016 m, 0.087 deg). `scripts/ci.sh` passes again after the fixes, with the same counts as above.
